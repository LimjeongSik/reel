# 포트폴리오 원고 → work/portfolio.md

먼저 이 스킬 폴더 기준 `../../shared/writing-rules.md`를 읽는다.
입력: `work/profile.md`, `work/cases/*.md`, `work/images/images.md`(있으면), `scripts/change-log.sh`의 출력(변경 기록용, 아래 "변경 기록 쓰는 법"). `/reel:cut`이 입력 경로(예: `profile.new.md`)를 넘겼으면 그 경로를 읽는다(`../../shared/work-layout.md` "입력").

## 이력서와 무엇이 다른가

이력서는 고르는 문서고, 포트폴리오는 **보여 주는** 문서다. 이력서에서 잘라 낸 과정 · 코드 · 화면이 여기 온다.
그래도 읽는 사람은 바쁘다 — 카드 → 배경 → 사례 순으로, 위에서 멈춰도 핵심이 전달되게 쓴다.

## 필드 단위로 쓰는 이유

사용자의 포트폴리오 사이트는 콘텐츠를 데이터 파일(예: `src/data/projects.ts`)로 관리한다.
원고를 **사이트 데이터의 필드 이름과 같은 단위**로 나눠 두면, 사람이든 Claude든 필드마다 복사해 넣기만 하면 된다.
필드 대응표는 `references/site-fields.md`에 있다 — 사용자가 사이트에 옮겨 달라고 하면 그 파일을 읽는다.
노션 · PDF로 쓸 때도 같은 구조가 그대로 섹션이 된다.

## 출력 형식 — work/portfolio.md

````markdown
# <프로젝트명> — 포트폴리오 원고

## 카드
| 필드 | 값 |
|---|---|
| slug | <slug> |
| title | <프로젝트명> |
| summary | 한 줄 소개 (40자 안팎, 무엇을 하는 서비스인가) |
| year | YYYY |
| period | YYYY.MM — YYYY.MM |
| role | 예: 앱 개발 1인(설계 · 개발) |
| platform | mobile / web |
| tech | React Native, Expo, TypeScript, … |
| thumbnail | images/<slug>-thumb.webp |
| icon | images/<slug>-icon.webp |
| links | demo: … · repo: … |

## 배경 (context)
- 사용자는 누구고 어떤 상황에서 쓰나
- 그래서 어떤 기술 요구가 생겼나
(2~4 문단 또는 bullet. 각 항목은 한 문단)

## 접근 (approach)
- 구조 · 설계에서 내린 큰 결정 2~4개와 그 이유

## 사례 (cases)

### ① <label: 사례 제목>
- **problem**: …
- **approach**: …
- **result**: …
- **metrics**: `라벨: 값` (있을 때만, 최대 3개)
- **changes**:
  - file: `경로` · commit: `해시 · YYYY.MM.DD`
  - before:
    ```ts
    ...
    ```
  - after:
    ```ts
    ...
    ```
  - note: 두 코드가 같은 입력에서 어떻게 다르게 움직였나

(cases/ 순서 그대로 3~6개)

## 변경 기록 (changelog)
> 범위: `<첫 해시 · YYYY.MM.DD>` ~ `<끝 해시 · YYYY.MM.DD>` · 내 커밋 n개 · 출처: change-log.sh

| 묶음 | 커밋 | 대표 변경 |
|---|---|---|
| 개선 | n | … |
| 기능 | n | … |
| 수정 | n | … |

### 개선 사항 (improvements)

#### <무엇이 나아졌나: 사용자나 개발자가 느끼는 변화가 보이게>
- **commits**: `abc1234 · 2026.07.12`, …
- **before**: 바뀌기 전 상태 한 문장 (커밋 · 코드에서 확인한 것)
- **after**: 바뀐 뒤 상태 한 문장
- **why**: 바꾼 이유 — 커밋 본문 · PR · 문서 · 이슈에 적힌 것만. 없으면 `<!-- TODO: 바꾼 이유 -->`
- **metrics**: `라벨: 전 → 후 (출처)` (실측값이 있을 때만, 최대 3개)
- **case**: ② (cases/에 같은 이야기가 있으면 번호만 적고 위 칸은 한 줄로)

(개선 3~8개, 날짜 순)

### 기능 추가 (features)
| 시기 | 기능 | 커밋 | 이유 |
|---|---|---|---|
| YYYY.MM | 한 줄 | `abc1234 · YYYY.MM.DD` | 한 줄 또는 `<!-- TODO -->` |

### 수정 (fixes)
| 시기 | 고친 현상 | 커밋 | 원인 |
|---|---|---|---|

## 화면 (screens)
| # | src | srcAlt | name | note |
|---|---|---|---|---|
| 1 | images/<slug>-screen-01-light.webp | images/<slug>-screen-01-dark.webp | 홈 | 그 화면에서 보이는 기능 한 줄 |

## 보조 이미지 (sheets)
| src | title | note |

## 회고 (선택)
- 다시 한다면 무엇부터 고칠지 1~3개. 근거 있는 것만.
````

## 쓰는 법

- 다 쓴 뒤 `../../shared/writing-rules.md` 5-1의 표로 문장을 한 번 더 고친다. 번역투 · 명사 나열 · 커밋 메시지 말투가 남아 있지 않게.
- 쓰기 전 `check`, 쓴 뒤 `record` — `../../shared/work-layout.md`의 덮어쓰기 규칙. 사용자가 고친 원고면 `*.new.md`에 쓴다.
- 완료 기록(`work-guard.sh mark work portfolio <TO>`)은 쓴 직후가 아니라 검수를 통과한 뒤에 남긴다 — `../../shared/work-layout.md` "완료 기록". `/reel:cut` 안에서는 커맨드가 남기고, 따로 불렸으면 아래 검수 뒤에 같은 조건으로 남긴다.
- 따로 불렸을 때만: 마지막에 `../../shared/scripts/check-work.sh work`를 돌려 오류(✗)를 고친다(고치는 범위는 work-layout.md "마무리 점검").

- problem · approach · result는 각각 2~4문장. cases/ 파일의 문제 · 해결 · 결과를 줄이되, 원인이 있던 층은 남긴다.
- changes의 코드는 cases/ 파일의 발췌를 그대로 옮긴다. 여기서 새로 줄이거나 다듬지 않는다.
- 화면 표의 note는 "화면 설명"이 아니라 "그 화면에서 보이는 기술적 포인트"(예: "회전 QR · 캡처 방지").
  `work/images/images.md`가 없으면 profile.md의 화면 목록으로 표를 만들고 src 칸에 `<!-- TODO: 캡처 -->`.
- 다 쓰고 나면 카드, 사례 제목, 개선 사항 제목 목록을 사용자에게 보여 준다(`/reel:cut` 안에서는 이유가 빈 묶음 같은 질문 항목과 함께 돌려준다). 사이트에 바로 옮기길 원하면 `references/site-fields.md`를 따른다.

## 변경 기록 쓰는 법

사례가 "가장 깊었던 문제 몇 개"라면, 변경 기록은 "프로젝트가 시간에 따라 어떻게 나아졌나"다.
분류와 숫자는 Claude가 세지 않고 스크립트로 센다 — 커밋이 많으면 눈으로 센 숫자는 틀린다.

범위는 `../../shared/work-layout.md` "단계별 기준 커밋"의 `portfolio` 단계 FROM/TO다. resume 모드로만 돌렸던 프로젝트라도
portfolio는 자기 기준부터 읽으므로 빠지는 커밋이 없다. 작성자 · 경로는 profile.md 머리말의 `작성자` · `귀속`을 그대로 쓴다.

```bash
S=<이 스킬 폴더>/scripts/change-log.sh
$S <저장소> <TO> --author a@x.com --author b@y.com                 # 전체(FROM 없음)
$S <저장소> <FROM>..<TO> --author a@x.com                          # 증분: 새 커밋만 보고 기존 기록 뒤에 붙인다
$S <저장소> <TO> --author a@x.com -- apps/mobile                    # 모노레포: 귀속 폴더 안의 변경만 센다
$S <저장소> <병합>^1..<병합>^2 --author a@x.com                     # 모노레포: 폴더로 합쳐지기 전 이력(귀속에 병합이 있을 때)
```

`--author`는 글자 그대로 찾고(정규식 아님), 여러 번 주면 그중 하나라도 맞는 커밋이다. 이름보다 이메일을 넘긴다.

출력은 커밋마다 분류(`feat` · `perf` · `refactor` · `fix` · `revert` · `docs` · `test` · `etc` …), 파일 수, 줄 수,
테스트 파일 수, 메시지에 적힌 수치, 본문 줄 수와 PR 번호다. 분류는 접두사가 없으면 낱말로 짐작한 것이니 제목을 읽고 바로잡는다.

### 1. 묶는다

커밋 하나가 아니라 **변경 하나** 단위로 쓴다. 같은 기능 · 같은 파일을 며칠에 걸쳐 고친 커밋들은 한 묶음이다
(`git show --stat`으로 파일이 겹치는지 본다). `docs` · `chore` · `style` · `ci`와 오타 · 포맷 커밋은 뺀다 — 읽는 사람의 판단에 쓰이지 않는다.

- **개선**: `perf` · `refactor`, 그리고 기존 동작을 더 낫게 바꾼 `feat`(이미 있던 화면 · 흐름을 빠르게 · 단순하게 · 안정적으로).
  "무엇이 나아졌나"를 before / after 한 문장씩으로 말할 수 있어야 개선이다. 말할 수 없으면 기능이나 수정으로 보낸다
- **기능**: 새로 생긴 것. 표에 한 줄씩
- **수정**: `fix` · `revert`. 사용자가 겪은 현상과 원인을 한 줄씩. 원인이 커밋에 없으면 원인 칸은 `<!-- TODO -->`
- cases/에 이미 있는 이야기는 다시 풀지 않고 `case: ②`로 잇는다(writing-rules 3장)

### 2. 이유를 찾는다 — 순서대로, 찾은 곳만

1. 커밋 본문(출력의 "본문(이유)"가 `n줄`이면 `git show -s <hash>`로 읽는다)
2. PR 본문 — 제목에 `(#123)`이 있고 `gh`를 쓸 수 있으면 `gh pr view 123 --json body`
3. 같은 시기에 바뀐 문서 · `CLAUDE.md` · 코드 주석(`git show <hash>`의 diff 안 주석)
4. 이슈 번호(`#123`, `closes`)가 있으면 그 이슈

넷 다 없으면 이유를 짐작해 쓰지 않는다. `<!-- TODO: 바꾼 이유 -->`로 남기고 마지막에 이유가 빈 묶음 목록을 사용자에게 묻는다.
"왜 바꿨나"는 면접에서 가장 먼저 나오는 질문이라 지어낸 이유가 가장 빨리 무너진다(writing-rules 1장).

### 3. 수치를 붙인다 — 잴 수 있는 것만

| 수치 | 구하는 법 | 쓸 때 |
|---|---|---|
| 메시지 · 문서에 적힌 실측값 | 출력의 "메시지 속 수치", 문서 grep | 출처(커밋 해시)와 함께. 가장 강한 근거 |
| 테스트 수 전 → 후 | `git grep -cE '^\s*(it\|test)\(' <hash>^ -- <테스트 경로>`와 `<hash>`에서 같은 명령 | 안정성 개선 · 수정에 |
| 의존성 추가 · 제거 | `git diff <hash>^ <hash> -- package.json`(매니페스트) | 라이브러리를 걷어 낸 개선에 |
| 코드 규모 전 → 후 | 같은 파일을 `git show <hash>^:<file> \| wc -l`과 `<hash>`에서 | 단순화한 개선에만. 늘어난 줄 수는 성과가 아니다 |
| 바뀐 파일 · 줄 수 | 출력의 "파일" · "줄" | 헤드라인에 쓰지 않는다. 변경 범위를 설명할 때만 |

- 재지 않은 값("약 2배 빨라짐", "체감상 개선")은 쓰지 않는다. 사용자가 실측값을 알고 있으면 묻고, 출처를 `사용자 확인`으로 적는다
- 숫자를 직접 센 명령은 metrics의 출처 칸에 그대로 남긴다 — 다시 세 볼 수 있어야 한다
- 같은 수치가 사례(cases) 칸에 이미 있으면 변경 기록에서는 빼고 `case: ②`만 둔다
