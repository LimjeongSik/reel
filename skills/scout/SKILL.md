# 프로젝트 분석 → work/profile.md

먼저 이 스킬 폴더 기준 `../../shared/writing-rules.md`와 `../../shared/work-layout.md`를 읽는다.
이 단계의 목적은 **글을 쓰는 것이 아니라 근거를 모으는 것**이다. 이후 스킬들은 여기 적힌 사실만으로 글을 쓰므로,
여기서 빠진 사실은 결과물에도 빠지고, 여기서 잘못 적힌 사실은 이력서에 그대로 실린다.

## 1. 나를 정한다

git 저장소라면 `git config user.name` / `user.email`과 `git shortlog -sne --all`을 비교해 "내 커밋"을 정한다.
같은 사람이 이메일 여러 개(회사 메일, GitHub noreply 등)로 커밋했을 수 있으니 이름이 같은 줄은 합쳐서 센다.
작성자가 여러 명이고 어느 쪽이 사용자인지 확실하지 않으면 사용자에게 묻는다 — 남의 작업을 내 것으로 쓰면 안 된다.
git이 아니면 그 사실을 적고, 기여 범위는 `TODO`로 남긴다.

**대상이 저장소의 하위 폴더일 때(모노레포).** `git rev-parse --show-toplevel`로 git 루트를 먼저 확인한다.
경로로 거른 로그(`git log -- <폴더>`)는 하위 폴더가 다른 저장소에서 합쳐진 경우(subtree merge, "history preserved")
그 전 이력을 놓친다 — 그때 파일은 `src/...`처럼 접두사 없는 경로에 있었다. 커밋 수 · 기간 · 사례 후보는
작성자 기준(`git log --all --author=<나>`)으로 찾고, 루트의 다른 폴더(서버 · 인프라)를 누가 맡았는지 함께 적는다.
`git show <hash>:<file>`도 그 커밋 시점의 경로로 써야 한다.

**AI 공동 작성 커밋.** 커밋 메시지에 `Co-Authored-By: Claude`(또는 다른 AI 도구), "codex 리뷰 반영" 같은 흔적이 있으면
비율을 세서 profile의 "작업 방식"에 사실로 적는다. 숨기거나 빼지 않는다 — 면접에서 반드시 나오는 질문이다.
대신 "확인 필요"에 "본인이 판단 · 검증한 부분(원인 추적, 되돌리기 결정, 리뷰 지적 채택 · 기각)"을 묻는 항목을 넣는다.

**커밋되지 않은 변경.** `git status --short`로 작업 트리를 본다. 변경이 있으면 profile 머리말에 적고,
코드 발췌는 커밋된 이력에서만 가져온다(작업 트리 코드는 사용자가 아직 고치는 중일 수 있다).

## 2. 읽는 순서

1. `README*`, `CLAUDE.md`, `docs/` (진행 문서 · 결정 기록 · 함정 노트가 있으면 사례의 보물창고다)
   - **이미 쓰인 정리 문서를 먼저 찾는다**: `grep -rliE '포트폴리오|portfolio|개선 기록|회고|retrospective|트러블슈팅|성능 측정' docs/ *.md`.
     있으면 실측 수치 · 문제/원인/해결이 이미 정리돼 있을 가능성이 크다. 그 문서의 수치는 출처로 쓰되,
     문서가 쓰인 시점(마지막 커밋 날짜) 이후의 커밋은 따로 확인한다 — 문서가 최신이 아닐 수 있다.
   - 하위 폴더마다 `CLAUDE.md`가 있으면 모두 읽는다. "왜", "사용자 피드백", 실측 수치가 거기 적혀 있는 경우가 많다.
2. 매니페스트: `package.json`, `app.json`/`app.config.*`, `pyproject.toml`, `build.gradle`, `Podfile` 등 → 스택 · 버전 · 스크립트
3. 진입점과 라우팅 → 화면(페이지) 목록. 이것이 shots의 촬영 목록이 된다
4. 데이터 · 상태 계층(API 클라이언트, 쿼리, 스토어, 인증), 네이티브 모듈, 테스트
5. git 이력: `git log --author=<나> --date=short --pretty='%h %ad %s'`, 첫 커밋 · 마지막 커밋, 큰 변경
   (`git log --author=<나> --shortstat`), `fix`·`perf`·`refactor`·`revert` 같은 메시지

저장소가 크면 `scout-analyst` 에이전트에 하위 영역별 조사를 맡기고 요약만 받아도 된다.

## 3. 사례 후보 고르기

좋은 사례는 "원인이 한 겹 아래에 있던 문제"다. 다음 신호를 찾는다.

- 같은 파일을 여러 번 고친 흔적(처음 해결이 틀렸고 다시 고친 이야기)
- 라이브러리 · OS · 브라우저 한계를 우회한 코드, 네이티브 모듈
- 경쟁 상태 · 중복 실행 · 캐시 · 토큰 갱신 · 백그라운드 동작
- 측정 전후가 남은 성능 작업
- 문서의 "함정", "주의", "왜" 메모와 코드 주석

후보마다 관련 커밋과 "왜 채용 담당자에게 의미 있는가" 한 줄을 적고, 강한 순서로 정렬한다. 5~8개면 충분하다.

## 4. 출력: work/profile.md

```markdown
# <프로젝트명> — 프로젝트 프로필

> slug: `<slug>` · 근거: 이 저장소 @ <HEAD 짧은 해시> (<YYYY.MM.DD>) 기준

## 한눈에
| 항목 | 내용 | 근거 |
|---|---|---|
| 한 줄 소개 | | README 1행 |
| 종류 · 플랫폼 | 웹 / iOS · Android 앱 / 라이브러리 … | |
| 기간 | 첫 커밋 ~ 마지막 커밋 | git log |
| 내 기여 | 커밋 n / 전체 m, 주로 맡은 영역 | git shortlog |
| 팀 | <!-- TODO --> | 저장소로 알 수 없음 |
| 규모 | 화면 n개 · 라우트 n개 · 테스트 n개 | 실제로 센 명령 |
| 링크 | 배포 URL · 스토어 · repo | |
| 작업 방식 | AI 공동 작성 커밋 비율 · 리뷰 도구 등 (있을 때만) | 커밋 메시지 |

## 기술 스택
분류별(언어 / 프레임워크 / 상태 · 데이터 / 스타일 / 네이티브 / 테스트 / 배포). 버전은 매니페스트 기준.

## 구조
진입 흐름, 주요 디렉터리, 데이터 · 인증 흐름을 5~10줄로.

## 화면 목록
| # | 화면 이름 | 경로 · 파일 | 무엇을 보여 주나 |

## 사례 후보
| # | 제목(가칭) | 관련 커밋 | 왜 의미 있나 |

## 저장소에 기록된 실측값
| 값 | 무엇 | 출처(파일:줄 또는 커밋) |

## 확인 필요
- 사용자에게 물어야 채울 수 있는 것 목록
```

숫자를 셀 때는 실제 명령(`grep -c`, `find | wc -l`, 테스트 러너의 목록 출력)을 쓰고 근거 칸에 적는다.
다 쓰고 나면 "확인 필요" 목록을 사용자에게 보여 주고, 답할 수 있는 것은 바로 받아 반영한다.
