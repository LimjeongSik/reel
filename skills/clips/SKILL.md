# 기술 사례 추출 → work/cases/

먼저 이 스킬 폴더 기준 `../../shared/writing-rules.md`(특히 1 · 2 · 6장)와 `../../shared/work-layout.md`(덮어쓰기 규칙)를 읽는다.
입력은 `work/profile.md`의 "사례 후보"다. 없으면 scout를 먼저 실행한다.

사례 파일은 결과물 전체의 원재료다. 이력서는 여기서 한두 줄을, 포트폴리오는 여기서 문단을 가져간다.
그래서 이 단계에서는 **줄이지 말고 근거를 빠짐없이** 담는다. 줄이는 일은 뒤 단계가 한다.

## 0. 이미 사례가 있으면 — 새 후보만

`work/cases/`에 파일이 있으면 기존 사례를 다시 쓰지 않는다. 사용자가 다듬었을 수 있고, 같은 커밋을 다시 읽는 건 낭비다.
- profile의 후보 중 `(새)` 표시이거나 cases/ 어느 파일의 "관련 커밋"에도 없는 후보만 새로 쓴다. 번호는 마지막 번호 다음부터
- 기존 사례의 관련 파일이 새 커밋에서 다시 바뀌었으면(`git log <지난 head>..HEAD -- <파일>`) 그 사례만 다시 볼지 사용자에게 묻는다
- 새 사례가 기존 것보다 강하면 순서를 바꾸자고 **제안만** 한다. 번호 변경은 resume · portfolio · images.md의 ①②까지 바뀌므로 사용자가 정한다

## 1. 사례 하나를 파고드는 법

1. 관련 커밋을 읽는다: `git show --stat <hash>`, `git show <hash> -- <file>`
2. 바뀌기 전 코드: `git show <hash>^:<file>`, 바뀐 뒤: `git show <hash>:<file>`
3. 같은 자리를 다시 고친 커밋이 있는지 본다: `git log --follow -p -- <file>` — "처음 고친 게 틀려서 다시 고쳤다"는 흐름은 가장 설득력 있는 이야기다
4. 관련 테스트, 문서 메모, 커밋 메시지 본문에서 원인 · 검증 방법 · 수치를 찾는다
5. 원인이 어느 층에 있었는지 한 문장으로 말할 수 있을 때까지 읽는다. 말할 수 없으면 아직 사례가 아니다

## 1-1. 기록에 없는 이유를 만들지 않는다

사례를 쓰다 보면 "버린 대안", "왜 이 방법을 골랐나", "어떻게 원인을 찾았나"를 그럴듯하게 채우고 싶어진다.
이것들은 커밋 메시지 · 코드 주석 · 문서에 **적혀 있을 때만** 쓴다. 적혀 있지 않으면:
- 해결 칸의 버린 대안은 빼고,
- 면접 포인트의 답은 `(저장소에 기록 없음 — 직접 답을 정리)` + `<!-- TODO -->`로 남긴다.
면접관이 "왜 그 대안을 버렸나"를 물으면 사용자가 실제로 답해야 한다. 지어낸 이유는 거기서 무너진다.

테스트로 고정했다고 쓸 때도 테스트 이름(`it(...)`)을 확인하고, 테스트가 실제로 덮는 상황만 적는다
(예: "버퍼가 찬 상황"을 재현하는 테스트가 없으면 그렇게 쓰지 않는다).

## 2. 코드 발췌 규칙

- 전 · 후 각각 핵심 5~15줄. 같은 파일 · 같은 자리여야 비교가 된다
- 줄임은 `// ...`만. 변수명 바꾸기 · 정리 · 의사 코드 금지 — 원 저장소에서 확인할 수 있어야 한다
- 새로 추가된 코드라 "전"이 없으면 전 칸을 비우고 "이 커밋에서 새로 추가"라고 쓴다. 전 코드를 지어내지 않는다
- 발췌는 커밋된 이력(`git show <hash>:<file>`)에서만. 작업 트리의 커밋 안 된 코드는 쓰지 않는다
- 시크릿 · 내부 URL · 개인정보가 보이면 `<redacted>`로 가린다

## 3. 출력 형식 — work/cases/NN-<slug>.md

````markdown
# ① <사례 제목: 사용자가 겪은 현상이 보이게>

- 관련 커밋: `abc1234 · 2026.07.12`, `def5678 · 2026.07.14`
- 확인 수준: 실기기 확인 / 테스트로 고정 / 정적 검증만 / 미확인
- 키워드: 토큰 갱신, 경쟁 상태, TanStack Query  ← 이력서 검색어로 쓸 것

## 문제
현상 → 원인(어느 층에서, 왜). 3~6문장.

## 해결
무엇을 어떤 기준으로 바꿨나. 버린 대안이 있으면 한 줄.

## 전 → 후
### `src/api/client.ts` · `abc1234 · 2026.07.12`
**전**
```ts
...
```
**후**
```ts
...
```
같은 입력에서 어떻게 다르게 움직이나: 한두 문장.

## 결과
무엇이 달라졌고 어디까지 확인했나. 수치는 출처와 함께.

| 지표 | 전 | 후 | 출처 |   ← 수치가 있을 때만

## 한 줄 요약
이력서 bullet로 바로 쓸 수 있는 한 문장(행동 + 기술 + 결과).

## 면접 포인트
- 예상 질문: …
  - 답의 실마리: …
````

번호는 강한 순서대로 `01`, `02` … 파일명 slug는 영문 소문자-하이픈. 제목의 원문자(①②…)도 같은 순서.
이 번호가 이력서 · 포트폴리오의 사례 순서가 되므로(뒤 스킬은 순서를 바꾸지 않는다), "강한 순서"를 정할 때 함께 본다:
- 이 프로젝트만의 문제가 먼저(이 프로젝트의 기술 · 도메인이 드러나는 것). 다른 프로젝트에서도 할 수 있는 이야기는 뒤로
- 사용자의 기존 이력서(아래 2-1)에 이미 같은 종류의 이야기가 있으면 뒤로 보내고 파일 첫머리에 겹친다고 적는다

## 2-1. 기존 이력서와 겹치는지 확인

사용자의 기존 이력서 · 경력기술서(예: `~/Desktop/Portfolio/resume/resume.md`)가 있으면 프로젝트 상세의 사례 제목들을 훑는다.
같은 종류의 사례(예: "동시 요청의 토큰 갱신을 한 번으로")가 다른 프로젝트에 이미 있으면 사례 파일 머리에
`- 겹침: <프로젝트> <사례> — 이력서 전체에선 하나만`을 적는다.

## 4. 마무리

- 다 쓴 뒤 `../../shared/writing-rules.md` 5-1의 표로 문장을 한 번 더 고친다. 번역투 · 명사 나열 · 커밋 메시지 말투가 남아 있지 않게.
- 파일마다 쓰기 전 `check`, 쓴 뒤 `record`(덮어쓰기 규칙). 다 쓰면 `../../shared/scripts/check-work.sh work`로 커밋 해시 · 날짜와 번호를 확인한다.

모든 사례를 쓴 뒤 사용자에게 사례 목록(제목 · 한 줄 요약 · 확인 수준)을 보여 주고,
뺄 것 · 순서를 바꿀 것 · 추가로 알고 있는 수치가 있는지 묻는다. 사용자가 기억하는 맥락(실기기 확인 여부,
사용자 반응)은 저장소에 없는 경우가 많고, 그게 사례를 가장 강하게 만든다.
