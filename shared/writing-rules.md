# 작성 원칙 (모든 스킬 공통)

이 플러그인이 만드는 글은 채용 담당자와 면접관이 읽는다. 읽는 사람은 "이 사람이 실제로 무엇을 했고,
그게 사실인가"를 판단하려 한다. 아래 원칙은 모두 그 판단을 돕고, 면접에서 공격받지 않게 하기 위한 것이다.

## 1. 근거 없는 것은 쓰지 않는다

- 수치는 **저장소에 기록된 실측값**만 쓴다(문서, 커밋 메시지, 테스트 수, 측정 스크립트 결과 등).
  출처를 함께 적는다. 그럴듯한 추정치("성능 30% 향상")는 면접에서 근거를 물으면 무너진다.
- 저장소로 알 수 없는 사실(기간, 팀 규모, 사용자 수, 회사명, 역할)은 지어내지 않고
  `<!-- TODO: 무엇을 채워야 하는지 -->`로 남긴다. 나중에 `grep TODO`로 한 번에 찾을 수 있다.
- 코드 발췌는 git 이력에서 **그대로** 가져온다. 줄일 때는 `// ...`만 쓴다. 다듬은 의사 코드는 넣지 않는다.
- "왜 그렇게 했나", "버린 대안", "어떻게 찾았나"도 사실이다. 커밋 · 주석 · 문서에 적혀 있을 때만 쓰고, 없으면 `TODO`로 묻는다.
- 확인 수준을 정직하게 적는다: `실기기 확인` · `테스트로 고정` · `정적 검증만` · `미확인`.
  "해결했다"고만 쓰면 어디까지 검증했는지 물었을 때 답이 엇갈린다.

## 2. 조건을 붙인다

OS · 기기 · 환경에 따라 달라지는 문장에는 조건을 붙인다("근무 중", "Android 11 이상에서", "삼성 기기의 벨소리 모드에서").
조건 없이 세게 쓴 문장은 반례 하나로 신뢰를 잃는다.

## 3. 같은 이야기를 두 번 쓰지 않는다

- **경력 항목**에는 조직 안의 역할과 영향(리드, 리뷰, 구조 설계, 출시 · 운영)을.
- **프로젝트 항목**에는 기술 문제와 해결을.
- 같은 수치는 한 문서에 한 번만 쓴다. 여기서 "한 문서"는 **실제로 함께 읽히는 단위**다 — resume.md처럼 길이별 원고를
  한 파일에 담은 경우, 1장(짧은 버전) · 3장(상세) · 4장(자기소개)은 서로 다른 칸에 따로 붙이므로 각각이 한 문서다.
  한 덩어리 안에서 같은 수치가 두 번 나오지 않게만 한다.

## 4. 고르는 문서다

이력서는 다 보여 주는 문서가 아니라 고르는 문서다. 깊은 설명은 포트폴리오로 넘긴다.
채용 판단에 의미 있는 수치만 남긴다(렌더링 1,300.9ms → 32.6ms 같은 것). 파일 개수, 번들 크기,
도구 개수처럼 판단에 쓰이지 않는 숫자는 뺀다. 기술 목록도 "한 번 써 본 것"이 아니라 반복해서 쓴 것 위주로.

## 5. 문장

- 합니다체. 짧고 쉬운 한국어. 번역투와 과장된 형용사("혁신적인", "획기적으로")는 쓰지 않는다.
- 한국어 개발자가 읽고 바로 이해하는 문장으로 쓴다. 영어 문장을 옮긴 것처럼 읽히면 고친다(아래 5-1).
- 태도 문장("열정적인 개발자")이 아니라 실제로 일하는 방식을 쓴다.
- 기술 용어는 정식 명칭(TanStack Query, React Native, Expo)으로 — 채용 검색에 걸린다.
- 비공개 고객사명 · 행사명은 밝히지 않고 성격만 적는다("대형 음악 페스티벌").

### 5-1. 어색한 한국어 고치기

다 쓴 뒤 소리 내어 읽듯 한 번 더 읽고, 아래 같은 문장이 있으면 고친다.

| 어색한 표현 | 고친 표현 |
|---|---|
| ~를 통해 해결했습니다 | ~로 해결했습니다 / ~해서 해결했습니다 |
| ~에 있어서, ~에 대해(서) 진행했습니다 | ~에서, ~를 했습니다 |
| ~하는 것이 가능했습니다 / ~할 수 있게 되었습니다 | ~할 수 있었습니다 / ~합니다 |
| ~되어지다, ~되어졌습니다 | ~되다, ~됐습니다 |
| 그것은 ~ 때문이었습니다 (대명사 주어) | 원인은 ~였습니다 / 주어를 빼고 바로 이유를 |
| 성공적으로 구현했습니다, 효과적으로 개선했습니다 | 구현했습니다 + 무엇이 달라졌는지 |
| 다양한, 여러 가지 (근거 없는 수식어) | 실제 개수나 이름 |
| 명사 나열 ("토큰 재발급 로직 개선 작업 진행") | 동사로 풀기 ("토큰을 다시 발급하는 코드를 고쳤습니다") |

- 한 문장에는 한 가지만. 쉼표로 세 가지 이상 이어지면 문장을 나눈다.
- 주어와 서술어가 맞는지 본다("문제는 ~ 고쳤습니다" ✗ → "~ 문제를 고쳤습니다").
- 영어 용어를 한국어 조사에 바로 붙일 때 읽히는 소리에 맞춘다("Query를", "Proxy로", "Activity가").
- 코드 이름(`useInsertionEffect`)은 백틱으로 감싸고, 그 앞뒤 문장은 코드를 모르는 사람도 읽히게 쓴다.
- 커밋 메시지 · 코드 주석의 말투(명사형 종결, "~함", "~ 방지")를 그대로 옮기지 않는다. 원고는 합니다체로 다시 쓴다.

## 6. 사례 구조

모든 기술 사례는 **문제 → 해결 → 전 → 후 → 결과** 순서다.

- 문제: 사용자가 겪은 현상 + 원인이 있던 층(라이브러리 한계, OS 정책, 경쟁 상태 등)
- 해결: 무엇을 어떤 기준으로 바꿨나. 버린 대안이 있으면 한 줄
- 전 → 후: 같은 자리의 코드가 어떻게 바뀌었나 + 커밋 `짧은해시 · YYYY.MM.DD`
- 결과: 무엇이 달라졌고 어디까지 확인했나(수치가 있으면 수치)
